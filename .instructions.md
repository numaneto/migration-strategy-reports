# Migration Strategy Analysis — Domain Rules

These rules ALWAYS apply when working with migration strategy reports or any customer artifacts in this folder. The report adapts to **any workload type** — Applications, Infrastructure, Databases, or any combination.

---

## ABSOLUTE RULES (NO EXCEPTIONS)

### Customer Data Isolation
- When a customer name is specified, ONLY read files from that customer's exact folder under `Customers/`
- **NEVER** cross-reference, read, copy from, or peek at ANY other customer folder — not even for "template reference", CSS examples, or report structure inspiration
- Each customer folder is a completely isolated engagement — treat as separate NDAs
- If the customer name is ambiguous (e.g., similar folder names could match more than one customer), **ASK the user** — never guess
- Report template, CSS, slide structure, and generation logic come ONLY from `migration-strategy-report/SKILL.md` — never from another customer's generated report
- **Violation log:** 2026-05-13 — read another customer's folder while working on a different customer's engagement. This must never happen again.

### Excel Sheet Completeness
- When loading Excel files, **list ALL sheet names first** and load every sheet that contains data
- Do NOT assume single-sheet workbooks — always check `sheetnames` programmatically before loading
- Empty sheets (0 data rows) or legend/reference sheets can be skipped, but must be explicitly checked and documented in console output
- Sheets with partial data (few non-null columns) should be examined and included if they contain any unique information not available in other sheets

Before generating any report, **scan the entire project folder** to discover all available inputs. This skill is NOT limited to CMDB data — it works with whatever artifacts exist:

- CMDB / portfolio exports (CSV, Excel, JSON)

**Determine slide composition AFTER analyzing all available evidence.** Only include slides where data is strong enough for a confident, leadership-ready narrative. 8 outstanding slides > 12 padded slides.

## Scope Identification (When CMDB/Portfolio Data Exists)

Every CMDB contains **Total Portfolio** (all apps in the dataset) and **In-Scope for Migration** (subset actually planned to move). These are NEVER the same number.

**How to identify In-Scope apps:**
1. Apps with a **Proposed Modernization Phase** assigned (non-blank, non-zero) = confirmed in-scope
2. Apps with a **Pilot Flag = Yes** = confirmed in-scope
3. Apps with **Retire strategy** assigned but still in a phase = in-scope (they need active decommission work)
4. Apps with **NO phase, NO pilot flag, AND strategy = Retain** = OUT of scope (staying as-is)

**Reporting rule:** Always report BOTH numbers prominently:
- "Total Portfolio: X apps" (everything in the CMDB)
- "In-Scope for Migration: Y apps" (actively planned to move/change)
- The Migration Execution Ownership split (Factory/Partner/Unknown) applies ONLY to in-scope apps
- The 6 Rs distribution applies ONLY to in-scope apps
- KPI cards must show both total and in-scope clearly

**Why this matters:** Reporting total portfolio as if it's all migrating inflates scope, misleads LT on effort/cost, and makes Factory/Partner splits meaningless. The in-scope number is what drives staffing, timeline, and budget.

## Infrastructure Migration Strategy Options (When Infra Workloads Detected)

When the assessment data is primarily **infrastructure-focused** (VMs, servers, data center migrations) rather than application CMDB, always evaluate and present these migration paths:

### Required Options to Assess

| Option | When to Recommend | Key Value Proposition |
|--------|------------------|----------------------|
| **Azure IaaS VMs (Lift & Shift)** | Default for all infra workloads; per-VM sizing and cloud-native services | Granular control, Azure-native monitoring, path to PaaS modernization |
| **Azure VMware Solution (AVS)** | VMware-based estates; large VM counts; operational continuity priority | VMware-native migration (vMotion), minimal change, fastest time-to-cloud |
| **Azure Arc (Hybrid Management)** | VMs that CANNOT move (regulatory, latency, data sovereignty, vendor lock-in); phased migration where some stay on-prem temporarily | Unified management plane, Azure Policy/Security from on-prem, bridge to full migration |

### Azure Arc — When to Propose as Option

**Always include Azure Arc as an option when ANY of these conditions exist:**
- Regulatory/compliance constraints prevent certain workloads from leaving on-premises
- Data sovereignty requirements mandate geographic residency that Azure regions don't satisfy
- Latency-sensitive workloads (real-time transaction processing, <1ms requirements)
- Vendor-locked applications that cannot be migrated without vendor cooperation
- Phased migration where some VMs will remain on-prem for 6–18 months during wave execution
- Edge/branch locations that will persist after data center exit
- Workloads with hardware dependencies (HSMs, specialized I/O, physical security)

**Azure Arc value to highlight:**
- Single pane of glass: manage on-prem + Azure VMs through Azure Portal
- Azure Policy enforcement on remaining on-prem servers
- Microsoft Defender for Cloud coverage across hybrid estate
- Azure Update Manager for patching on-prem servers
- Azure Monitor / Log Analytics for unified observability
- SQL Server enabled by Azure Arc for on-prem SQL instances
- Enables gradual migration without losing governance during transition
- ESU (Extended Security Updates) delivery for Windows Server 2012/2012 R2 via Arc

**Presentation rule:** Present Azure Arc as "Option: Hybrid Management" alongside the primary migration options. Frame it as a governance bridge and a path for workloads that cannot migrate immediately — NOT as an alternative to migration. Arc is complementary, not competing.

## Classification Rules — The 6 Rs

| Condition | Strategy |
|-----------|----------|
| Simple complexity + standard stack + <5 integrations + internally developed | **Rehost** |
| .NET Framework needing version upgrade + SQL upgrade + no major code rewrite | **Replatform** |
| High-value + needs containers/microservices + cloud-native scalability | **Refactor** |
| Vendor app with modern SaaS equivalent available | **Replace** |
| Low criticality (1) + Best Efforts RTO + redundant/unused | **Retire** |
| Mainframe/specialized hardware/vendor-locked + no viable migration path | **Retain** |

## Factory vs. Partner vs. Unknown Classification

### Standard Factory (Application CMDB Scenarios)

**Factory-eligible stacks** (Azure App Service / standard Azure PaaS):
- .NET / .NET Framework (all versions)
- Java (any version)
- Node.js, Python, PHP, Ruby
- Angular / React / Vue / Static Web
- SQL Server, MySQL, MariaDB, PostgreSQL

| Condition | Classification |
|-----------|---------------|
| Simple/Medium + App Service-supported stack + <5 integrations + internal + no vendor dependency | **Factory** |
| Complex/Very Complex + vendor-supplied + >10 integrations + multi-DB + clinical protocols + mainframe | **Partner** |
| 2+ fields = "Data not available" + no complexity rating + undefined architecture + no owner | **Unknown** |

### Database Factory vs Partner (When DB-Level Data Exists)

| Condition | Classification |
|-----------|---------------|
| SQL Server 2012+ with <5 dependent apps, DMA "Ready", <500 GB, no cross-DB deps | **Factory — Azure SQL DB/MI via DMS** |
| PostgreSQL / MySQL / MariaDB / MongoDB / Cassandra → managed Azure equivalent | **Factory — Azure managed DB via DMS** |
| Oracle (any version) — requires licensing expertise, potential refactor | **Partner** |
| DB2 / Teradata / Sybase / Informix — schema refactoring needed | **Partner** |
| Any DB with 500+ stored procedures or heavy CLR usage | **Partner — remediation first** |
| Shared data hub DB serving 5+ applications | **Partner — coordination complexity** |
| No DMA assessment + no version info + no size data + no owner | **Unknown** |

### GHCP-Enabled Factory (Cross-Cloud Migration Scenarios)

**Critical Rule:** Anything that GitHub Copilot (GHCP) App Modernization Extension can handle via automated assessment and code conversion is **Factory-eligible**, because it has tooling-assisted migration paths that reduce manual effort to repeatable, accelerated patterns.

**GHCP App Mod Extension Capabilities = Factory:**

| AWS Source | Azure Target | GHCP Capability | Factory Classification |
|-----------|-------------|-----------------|----------------------|
| AWS Lambda | Azure Functions | Automated assessment + code conversion | **Factory** |
| ECS/Fargate (containerized) | Azure Container Apps | Kubernetes/container migration tooling | **Factory** |
| EKS (Kubernetes) | Azure Container Apps / AKS | Kubernetes migration + manifest conversion | **Factory** |
| App Runner | Azure Container Apps | Container migration (simple) | **Factory** |
| API Gateway + Lambda | Azure Functions + API Management | Serverless migration pattern | **Factory** |
| S3 (static web hosting) | Azure Blob Storage / Static Web Apps | Storage migration (data copy) | **Factory** |
| RDS (PostgreSQL/MySQL) | Azure Database for PostgreSQL/MySQL | Database migration (DMS tooling) | **Factory** |
| RDS (SQL Server) | Azure SQL | Database migration (DMS tooling) | **Factory** |
| DynamoDB | Azure Cosmos DB | NoSQL migration (documented pattern) | **Factory** |
| SQS | Azure Service Bus / Storage Queues | Messaging pattern swap | **Factory** |
| SNS | Azure Event Grid / Service Bus Topics | Pub/sub pattern swap | **Factory** |
| CloudFront + S3 | Azure Front Door + Blob/Static Web | CDN + origin migration | **Factory** |
| EventBridge | Azure Event Grid | Event routing pattern swap | **Factory** |
| Step Functions | Azure Durable Functions / Logic Apps | Workflow orchestration migration | **Factory** |
| Cognito | Azure AD B2C / Entra External ID | Identity migration (Partner if complex custom flows) | **Factory** (simple) / **Partner** (complex) |
| GCP Cloud Run | Azure Container Apps | Container migration tooling | **Factory** |
| GCP Cloud Functions | Azure Functions | Serverless migration | **Factory** |

**Partner-required (NO GHCP tooling):**

| AWS Source | Reason for Partner | Classification |
|-----------|-------------------|----------------|
| MSK (Kafka) | Complex stateful streaming, custom connectors | **Partner** |
| SageMaker (ML pipelines) | Custom model training, MLOps complexity | **Partner** |
| Bedrock (AI agents) | Custom AI orchestration, prompt engineering | **Partner** |
| Glue (complex ETL) | Custom ETL logic, data lake architecture | **Partner** |
| Kinesis Analytics | Real-time streaming analytics | **Partner** |
| Redshift | Data warehouse migration (complex schema + queries) | **Partner** |
| EMR (Hadoop/Spark) | Big data platform migration | **Partner** |
| IoT Core (complex) | Device management + custom rules | **Partner** |
| Multi-service orchestration (>5 tightly coupled AWS services) | Deep AWS-native coupling | **Partner** |

**Classification Decision Logic for Cross-Cloud:**
1. **Identify the primary compute/hosting pattern** (Lambda, ECS, EC2, etc.)
2. **Check GHCP capability table** — if a direct tooling path exists → Factory
3. **Assess integration count** — even with GHCP tooling, >10 tightly-coupled integrations may push to Partner
4. **Check for AWS-native lock-in** — services with no Azure equivalent require custom architecture → Partner
5. **When in doubt:** If GHCP can handle the primary workload but supporting services are complex, classify the primary workload as Factory and flag dependencies as risks

## MANDATORY Slide: Dependency Mapping (NEVER SKIP)

**Rule:** The Dependency Mapping slide MUST be included in every report where ANY of the following conditions are met:
- Integration count field is populated for ANY app in the dataset
- Architecture diagrams or dependency maps exist in artifacts
- Middleware/ESB references appear in any data (RabbitMQ, Kafka, BizTalk, MuleSoft, Cloverleaf, TIBCO, etc.)
- Cross-pillar data linking apps to databases/servers exists
- Questionnaire/intake data mentions integrations, APIs, file transfers, or async processes

**This is NOT optional.** Integration dependencies are the #1 cause of migration failures. If ANY dependency data exists, this slide MUST appear — even if data is partial or only covers a subset of apps. Partial dependency data is still critical for migration sequencing.

**Slide placement:** Immediately after Migration Execution Ownership, before Phased Roadmap.

**Minimum content (even with sparse data):**
- KPI cards: Total Dependency Points, High-Fan-Out Apps, Middleware Platforms, External Dependencies
- Bar chart showing middleware/integration platform distribution
- Table of highest-connectivity applications
- Cross-application dependency map (whatever detail is available)
- Migration Sequencing callout identifying dependency hubs that constrain migration order

**Why this rule exists:** This slide was previously omitted from a customer report despite the dataset having integration count data for the majority of apps and detailed dependency information for Phase 1 apps. Migration sequencing cannot be planned without dependency visibility.

## Phasing Logic

| Phase | Criteria |
|-------|----------|
| Phase 1 (Pilot) | Internally developed, high obsolescence, simple/medium, full code ownership |
| Phase 2–3 | Moderate complexity, expanding vendor coordination, proven patterns |
| Phase 4–5 | Complex clinical/mission-critical, deep integrations, zero-downtime |

| Phase 7 | Low-criticality bulk, batch retire |

## Input Data Expectations

### When CMDB Data Exists
CMDB fields expected: Application Name, Business Capability, Criticality Rating (1–4), Architecture Tier, Tech Stack/Framework, Database Platform, OS, Obsolescence Scores (Tech/DBMS/OS 1–5), Migration Complexity, Integration Count, Server Count, Containerized, Regulatory Requirements, RPO/RTO, Application Owner/BU, Vendor/Internal, Migration Phase, Pilot Flag.

Missing data should be explicitly marked "Data not available" — never left blank.

### When Infrastructure Data Exists (RVTools, Azure Migrate, vCenter, SCCM)
Infra fields expected: VM/Server Name, Physical vs Virtual, Hypervisor, CPU (vCPU), RAM (GB), Disk (GB), CPU/RAM Utilization %, Operating System, IP Address/VLAN, Datacenter/Cluster, Workload Type, Powered On, Snapshot Count, Environment (Prod/Dev/Test/DR), Owner/BU, Migration Phase/Wave.

Also look for: Network topology data (subnets, firewall rules, ExpressRoute/VPN, DNS zones), AD/identity data (domain controllers, forests, ADFS), storage inventory (SAN/NAS type, IOPS, backup solution), and load balancer inventory.

### When Database Data Exists (DMA, MAP Toolkit, Azure Migrate DB)
DB fields expected: DB Instance Name, DB Engine (with version), DB Size (GB), DB Count on Instance, HA Configuration, Stored Procedure Count, Cross-DB Queries, Linked Servers, CLR/Extended Features, Connection Count, Backup Size/RPO, Apps Dependent on DB, Target Azure Service, Migration Method, Migration Readiness, Regulatory/Compliance, Owner/DBA Team.

### When No Structured Data Exists (Narrative/Qualitative Artifacts Only)
Build the report from available evidence:
- Meeting notes → extract app names, decisions, blockers, timelines
- Architecture docs → infer integration complexity, system boundaries
- Vendor proposals → extract scope, timelines, ownership assumptions
- Assessment reports → pull technical debt, obsolescence, complexity
- WorkIQ results → stakeholder positions, discussed constraints, agreed actions

**Key rule:** Gaps are findings. If 40% of apps have no complexity rating, that IS a slide-worthy insight for leadership (recommends discovery workshop). Never pad with assumptions — flag what's missing and recommend next steps to close the gap.
